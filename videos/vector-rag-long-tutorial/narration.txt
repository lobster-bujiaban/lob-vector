相似度零点九二，系统却答错了；相似度只有零点六八，反而找到了正确答案。更离谱的是，它还把另一个客户的机密文档搜了出来。向量检索，到底靠不靠谱？

我们不背概念。今天直接抢救一个即将上线的客服知识库。老板只给你五次机会：修好错误答案、关键词漏检、权限泄露、回答幻觉和技术选型。五关都过，才算真正学会向量和 RAG。

第一关，相似度骗局。用户问：“接口返回四二九怎么办？”系统返回一段“接口请求成功”的文档，相似度零点九二。团队看到九十二，就以为有百分之九十二概率正确。错。相似度只表示两个向量在当前模型空间里有多接近，不是答案正确概率。

换一个 Embedding 模型，同一段文本可能从零点九二变成零点七五；Qdrant 显示的可能是相似度，另一个接口返回的可能是距离。一个越大越好，一个越小越好，数字根本不能直接横向比较。

真正的正确率要怎么来？准备十道有标准答案的问题。如果 Top 三结果命中八道，Recall at 3 才是百分之八十。MRR 看正确答案第一次出现得够不够靠前，NDCG 看整个排序质量。单条相似度不能加百分号；一组标注问题算出的指标，才能评价系统。

第一关结论：相似度负责排序，评估集负责证明质量。

第二关，向量为什么会找错？我们把文档画成语义地图。“幼犬患病如何处理”和“小狗生病怎么办”，文字不同，但真实 Embedding 会把它们放得很近。“苹果发布手机”和“苹果富含纤维”，词语相同，却会因为上下文不同被分开。

查询也会变成向量。系统比较查询向量和文档向量的方向，夹角越小，余弦相似度通常越高，然后取前 K 个候选。这就是 Top K。

但模型再好，也救不了错误分块。一个 Chunk 同时塞进退款、发票和账号安全，语义会被稀释；切得只剩“按以下步骤处理”，条件和结论又断开。Overlap 可以保留边界上下文，但太大就会重复召回、浪费 Token。

第二关结论：检索质量不是只换模型，而是 Embedding、Chunk 和 Top K 一起调。

第三关，四二九为什么搜不到？因为向量擅长语义，却不一定擅长错误码、型号和接口路径。BM25 正好相反，它根据关键词出现频率、稀有程度和文档长度打分。遇到“四二九”“E 一零零二七”“斜杠 API 斜杠 orders”，关键词检索经常更稳。

实战不是二选一。先让向量找同义表达，再让 BM25 找精确词。两路分数尺度不同，不能硬加。RRF 只看名次：同一个片段在两路都靠前，融合分就更高。

融合后候选太多怎么办？交给 Reranker，也就是重新排序模型。第一阶段宁可多找，第二阶段让模型同时阅读问题和候选，把真正相关的证据提到前面。注意，我说的是“重新排序”，不是重量的“重”。

第三关结论：向量负责语义，BM25 负责精确词，RRF 合并候选，Reranker 负责重新排序。

第四关，也是最危险的一关。租户 A 查询退款，结果里出现租户 B 的合同。能不能先搜出来，再在 Prompt 里写“不要泄露”？绝对不能。模型不是权限系统。

每个 Chunk 必须带 Metadata：来源、页码、租户、部门、角色和时间。数据库检索时先执行 tenant id、department、permission 过滤，再在合法范围内计算 Top K。权限必须先于相关性。

这时怎么选数据库？个人原型和本地知识库，用 Chroma，几行代码就能持久化。在线服务、多租户、字段过滤和快照恢复，用 Qdrant。向量走向千万级，需要分片、查询节点和多种索引，再评估 Milvus。数据只有几万条，别为了显得专业提前支付分布式成本。

第四关结论：Chroma 赢在轻，Qdrant 赢在生产过滤，Milvus 赢在规模；权限过滤永远不能交给提示词。

第五关，资料找对了，模型仍然可能胡说。完整 RAG 不是“向量库加大模型”六个字，而是一条证据流水线：问题先做 Embedding 和权限过滤，再跑向量与 BM25，融合、重新排序，最后把证据交给大模型。

Prompt 要写清楚：只能使用这些证据；每个结论标注一、二、三号来源；没有证据就拒答。生成后还要检查引用编号是否真实存在，并让用户能回到文件、章节和原文位置。引用不是装饰，它是答案的质检报告。

如果问题是“设备离线会怎样影响 Agent 工作流”，答案横跨多篇文档，普通 Top K 可能只找到局部。这时 LightRAG 可以抽取实体和关系，沿着“设备离线、工具失败、工作流降级”这条关系链查资料。local 查具体实体，global 查整体关系，mix 把图和原文合在一起。代价是建图更慢、模型调用更多、更新更复杂。

如果你的痛点不是关系推理，而是几十个人要上传 PDF、检查切片、调召回、看引用和维护知识库，那么需要的是 RAGFlow 这类平台。LightRAG 解决“知识之间有什么关系”，RAGFlow 解决“团队怎样生产和运营企业知识库”。

五关结束，给你一条不会走弯路的学习路线。第一步，手写内存检索，亲眼看 Chunk、向量、余弦相似度、Filter 和 Top K。第二步，用 Chroma 学持久化。第三步，用 Qdrant 学多租户权限，用 Milvus 学索引与规模。第四步，加 BM25、RRF、Reranker 和固定评估集。第五步，完成带引用、校验和拒答的 RAG。最后再学 LightRAG 的关系图，以及 RAGFlow 的平台能力。

最终选型只问五句话：数据有多大？问题靠语义还是精确关键词？有没有强权限？是否需要跨文档关系？知识库由开发维护，还是运营维护？

现在再看最开始的事故：零点九二答错，不代表向量不可靠；它说明你把相似度误当概率，而且缺少评估、关键词检索、重新排序和权限过滤。真正的生产级 RAG，不是选一个最贵的数据库，而是让每一层都能观察、能验证、能拒绝犯错。

如果你只记住一句话：相似度负责找候选，证据和评估才负责让答案可信。

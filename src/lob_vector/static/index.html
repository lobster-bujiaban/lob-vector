1. 如何安装与启动

本项目使用嵌入式 PersistentClient，不需要单独启动数据库进程；团队共享时再切换服务端模式。

本项目 · 推荐

uv 安装

依赖已写入 pyproject.toml，进入项目同步即可。

uv sync
独立项目

安装 Python 包

新项目可直接添加 Chroma 客户端和本地引擎。

uv add chromadb
服务端模式

启动共享服务

需要跨进程或多人连接时，运行 Chroma Server。

chroma run --path ./chroma-data

2. 什么场景适合 Chroma

Chroma 的优势是本地开发快、API 简单、Embedding 与 Metadata 一起管理；它不是所有规模下的默认答案。

适合

本地知识库与原型

个人资料问答、产品 Demo、几万到中小规模 Chunk，快速形成可持久化闭环。

适合

单机 AI 应用

应用与向量库部署在同一台机器，通过 PersistentClient 直接读写，无额外服务运维。

谨慎

复杂生产检索

强多租户权限、高并发、复杂过滤或超大规模时，应继续评估 Qdrant、Milvus 或服务端架构。

3. Chroma 提供哪些功能

Collection 是核心边界：一组文档、向量和 Metadata 在同一 Collection 内完成生命周期管理与检索。

Collection创建、获取、删除和隔离知识集合
Upsert / Update批量写入并按 ID 更新文档与向量
Vector QueryCosine / L2 / Inner Product 近邻查询
Metadata Filter查询前按来源、时间、租户等字段过滤
Delete按 ID、Metadata 或文档条件删除
Persistence应用重启后恢复 Collection 数据
自带 Embedding可托管向量化，也可像本项目传入外部向量
Client / Server支持嵌入式、服务端和云端形态

4. 数据保存在哪里

Chroma 本地持久化不是单独一个 SQLite 向量数据库，而是结构化数据与向量索引协同。

chroma.sqlite3Collection、文档、Metadata、ID 与系统表
HNSW 二进制目录data_level0.bin、link_lists.bin 等向量近邻索引文件

Chroma 和 Qdrant 到底差在哪

两者都能做向量检索和 Metadata Filter。真正的差异主要在部署复杂度、索引控制、多租户与扩展路径，而不是“小数据能不能返回 TopK”。

决策维度
Chroma
Qdrant
上手成本
更低PersistentClient 嵌入应用，原型几行代码即可运行。
中等本地模式简单；生产通常运行独立 Server。
过滤能力
Where Filter支持 Metadata、文档内容与逻辑组合，默认管理相关索引。
Payload Filter + 显式索引可按字段创建 Keyword、Integer 等 Payload Index。
多租户
按 Collection 隔离更直观适合原型、个人知识库和中小应用。
Payload / Shard Key 路径更完整适合共享集群中的租户过滤、分片与在线服务。
生产运维
轻量优先本地、单节点、Cloud 均可用；当前项目采用嵌入式模式。
服务化优先REST/gRPC、鉴权、监控、快照及分布式能力更贴近数据库服务。
主要代价
高级运维控制较少复杂多租户与精细索引实验不如 Qdrant 直接。
部署与维护成本更高需要管理服务、密钥、资源、备份和升级。
选 Chroma：先把 RAG 做出来

本地知识库、产品原型、单机 AI 应用、团队希望最少运维时优先。

选 Qdrant：把检索当在线基础设施

强权限、多租户、复杂结构化过滤、独立服务与持续扩展时优先。

同结果，不同工程边界

Chroma Where Filter / Qdrant Payload Filter
实验分两步：先验证 Chroma 与 Qdrant 在小数据上能返回相同的安全 TopK；再观察 Qdrant 无过滤时如何命中越权机密。耗时仅供观察，不构成性能基准。
运行后先看 Chroma / Qdrant 安全 TopK 是否一致，再看 Qdrant 如何拦截越权结果
